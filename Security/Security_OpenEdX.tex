\section*{How to Read This Document}
\addcontentsline{toc}{section}{How to Read This Document}

This document is structured to provide a comprehensive view of the security posture of the Moove Education Platform. To help you navigate and understand the content efficiently, please review the following conventions.

\subsection*{Document Structure}

The document is organized into the following main sections:

\begin{itemize}
    \item \textbf{Introduction}: Defines the purpose, scope, and relationship to other documents.
    \item \textbf{Deployment Architecture}: Describes the current production environment, including hardware, software, and container architecture.
    \item \textbf{Asset Identification \& Classification}: Lists and classifies assets per CMCSRS Annex B.
    \item \textbf{Threat Model}: Identifies strategic, tactical, and operational threats across four pillars: Governance, Human, Process, and Technology.
    \item \textbf{Risk Assessment}: Applies SGOC + PESTLE, BMIS, and ISO 27001 frameworks.
    \item \textbf{Security Controls Mapping}: Maps implemented and planned controls to CMCSRS requirements.
    \item \textbf{Security Assessment Findings}: An exhaustive list of findings, categorised by severity (Critical, High, Medium, Low), with evidence and status.
    \item \textbf{Remediation Plan}: Completed actions and remaining items with step-by-step guidance.
    \item \textbf{Compliance}: Alignment with INSA, CMCSRS, Computer Crime Proclamation, Electronic Signature Proclamation, and FDRE National Cybersecurity Policy.
    \item \textbf{Appendices}: Quick reference maps, glossary, remediation guides, and vulnerability logs.
\end{itemize}

\subsection*{Colour Coding and Status Indicators}

Throughout the document, you will encounter the following conventions:

\begin{itemize}
    \item \textbf{Table Headers}: All table headers are highlighted in \textcolor{mooveblue}{blue} for easy identification.
    \item \textbf{Captions}: Table and figure captions are displayed in \textcolor{mooveblue}{blue}.
    \item \textbf{Status Colours} (used in findings tables):
    \begin{itemize}
        \item \textcolor{green}{RESOLVED} – The finding has been fully addressed.
        \item \textcolor{orange}{PENDING} – The finding is acknowledged and remediation is in progress or planned.
        \item \textcolor{yellow}{UNKNOWN} – The finding requires further investigation or cannot be verified.
        \item \textcolor{gray}{INFORMATIONAL} – The finding is for awareness only and does not require action.
    \end{itemize}
    \item \textbf{Severity Levels}:
    \begin{itemize}
        \item \textbf{CRITICAL} – Immediate action required; high impact on confidentiality, integrity, or availability.
        \item \textbf{HIGH} – Action required within 7–14 days; significant security risk.
        \item \textbf{MEDIUM} – Action required within 30–90 days; moderate security risk.
        \item \textbf{LOW} – Action required as part of continuous improvement; low security risk.
    \end{itemize}
\end{itemize}

\subsection*{Finding Identifiers}

Each finding is assigned a unique identifier following the pattern:

\begin{center}
\textbf{SEVERITY-NUMBER}
\end{center}

Examples:
\begin{itemize}
    \item \texttt{CRIT-01} – First critical finding.
    \item \texttt{HIGH-04} – Fourth high-risk finding.
    \item \texttt{MED-02} – Second medium-risk finding.
    \item \texttt{LOW-03} – Third low-risk finding.
\end{itemize}

Resolved findings are prefixed with \texttt{RES-} (e.g., \texttt{RES-01}).

\subsection*{Evidence and References}

\begin{itemize}

These files are referenced in the \textit{Evidence} column of the findings tables.

\section*{Definitions}
\addcontentsline{toc}{section}{Definitions}

\begin{description}
    \item[Asset] Any data, device, or other component of the environment that supports information-related activities. Assets include hardware, software, information, and personnel.
    \item[Confidentiality] The property that information is not made available or disclosed to unauthorized individuals, entities, or processes (ISO/IEC 27000).
    \item[Critical Infrastructure] A computer system, network, or data whose compromise would cause considerable damage to public safety or national interest (CMCSRS).
    \item[Cyber Security] The protection of information systems from theft, damage, or disruption of the services they provide.
    \item[Integrity] The property of safeguarding the accuracy and completeness of assets (ISO/IEC 27000).
    \item[Penetration Testing] An authorised simulated cyber attack on a computer system, performed to evaluate the security of the system.
    \item[Risk] The potential that a given threat will exploit vulnerabilities of an asset or group of assets and thereby cause harm to the organisation.
    \item[Threat] A potential cause of an unwanted incident, which may result in harm to a system or organisation.
    \item[Vulnerability] A weakness of an asset or group of assets that can be exploited by one or more threats.
\end{description}

\section{Introduction}
% ---------------------------------------------------------------------

\subsection{Purpose}
This document defines the security architecture, threat model, risk assessment, and compliance posture for the Moove Education Platform (Powered by Open edX). It serves as the primary security reference for internal governance, external audits, and government compliance with INSA standards. The document is aligned with the Ethiopian Critical Mass Cyber Security Requirement Standard (CMCSRS), the National Cybersecurity Policy, and related INSA guidelines.

\subsection{Scope}
The scope covers the entire production deployment of the Moove Education Platform, including its containerised services (LMS, CMS, MFE, databases, caching, search, reverse proxy), data flows, user roles, and operational processes. It addresses security controls for confidentiality, integrity, and availability of learner, educator, and administrative data.

\subsection{Relationship to Other Documents}
This document builds upon:
\begin{itemize}
    \item \textbf{SRS}: Functional security requirements.
    \item \textbf{SDD}: System and network architecture.
    \item \textbf{TDD}: API specifications and database schemas.
    \item \textbf{User Guide}: End‑user security awareness.
\end{itemize}
It provides the strategic and tactical security overlay required for INSA compliance.

\section{Deployment Architecture (Current State)}
% ---------------------------------------------------------------------

Based on the latest security audit and remediation (June 17, 2026), the production environment is now fully hardened for all critical, high, and vulnerability-related issues:

\begin{itemize}
    \item \textbf{OS}: Ubuntu 22.04.5 LTS, kernel 5.15.0-185-generic.
    \item \textbf{Hardware}: 8 vCPUs (AMD EPYC-Rome), 15 GiB RAM, 150 GiB disk (34\% used).
    \item \textbf{Tutor Version}: 21.0.8 (running under non‑root user `tutor`).
    \item \textbf{Open edX Version}: 21.0.8-indigo (edx-platform release/ulmo.3).
    \item \textbf{Deployment Method}: Docker containers orchestrated by Tutor.
    \item \textbf{Hosting Provider}: Hetzner (KVM virtualization) through Web Hosting in Ethiopia - Yegara HOST.
    \item \textbf{Firewall}: UFW is active with only SSH, HTTP, and HTTPS allowed (CRIT‑02 resolved).
    \item \textbf{Secrets Management}: All hardcoded secrets rotated and stored securely (CRIT‑03,04,05,06 resolved).
    \item \textbf{Swap Usage}: 0 GiB of 7 GiB (CRIT‑07 resolved).
    \item \textbf{Kernels Installed}: 2 (HIGH‑04 resolved).
    \item \textbf{Fail2ban}: Active and running (HIGH‑06 resolved).
    \item \textbf{Trivy}: Installed with daily scheduled scans; all HIGH and CRITICAL vulnerabilities remediated (HIGH‑08 resolved).
    \item \textbf{Security Headers}: `X-Frame-Options: SAMEORIGIN` present (HIGH‑09 resolved).
    \item \textbf{DEBUG}: Disabled in LMS (HIGH‑10 resolved).
    \item \textbf{API Authentication}: OAuth2 enforced, Basic Auth removed (HIGH‑03 resolved).
\end{itemize}

\section{Risk Assessment (CMCSRS Framework)}
% ---------------------------------------------------------------------

\subsection{Strategic Assessment (SGOC + PESTLE)}

\subsubsection{Strengths}
\begin{itemize}
    \item Use of Tutor for standardised, reproducible deployment.
    \item Caddy for automatic HTTPS with Let's Encrypt.
    \item Containerization isolates services.
    \item Recent Ubuntu LTS (22.04) with security patches.
    \item MongoDB replica ready (single node).
    \item MySQL with binlog retention for point-in-time recovery.
    \item \textbf{All critical and high vulnerabilities resolved}:
    \begin{itemize}
        \item Tutor runs as non‑root user (CRIT‑01).
        \item UFW firewall active (CRIT‑02).
        \item All secrets rotated (CRIT‑03–06).
        \item Swap usage low (CRIT‑07).
        \item Docker group, kernels, Fail2ban, Trivy, headers, DEBUG fixed.
        \item All container image CVEs remediated (HIGH‑08).
        \item All medium and low findings resolved.
    \end{itemize}
\end{itemize}

\subsubsection{Gaps}
\begin{itemize}
    \item No dedicated security team or CISO.
    \item No security committee (T-GOV-05).
    \item No security awareness program (T-HUM-04).
    \item No security clearance process (T-HUM-05).
    \item No security training (T-HUM-06).
    \item Insufficient security budget (T-GOV-04).
\end{itemize}

\subsubsection{Opportunities}
\begin{itemize}
    \item Leverage open-source security tools (Wazuh, ELK, OSSEC).
    \item Adopt INSA's Cyber Security Career Path for staff.
    \item Implement SIEM with open-source solutions.
    \item Implement ISO 27001 controls gradually.
\end{itemize}

\subsubsection{Challenges}
\begin{itemize}
    \item Resource constraints for security team.
    \item Compliance deadlines.
    \item Limited security expertise in-house.
\end{itemize}

\section{Security Assessment Scripts}
% ---------------------------------------------------------------------

The following script now reflects the hardened environment and checks for all resolved findings.

\begin{lstlisting}[language=bash, caption={assess\_security.sh (enhanced)}]
#!/bin/bash
# Comprehensive Security Assessment Script for Moove Education Platform
# Run with sudo
# Version: 4.0 (All Findings Resolved)

echo "=========================================="
echo " Moove Education Platform Security Audit"
echo " Date: $(date)"
echo " Version: 4.0"
echo "=========================================="

# 1. System and OS
echo -e "\n--- OS and Kernel ---"
uname -a
lsb_release -d
hostnamectl

# 2. Users and Groups
echo -e "\n--- Users with sudo/root ---"
grep -E "^sudo|^root" /etc/group
echo -e "\n--- Tutor user existence ---"
id tutor 2>/dev/null && echo "OK: User 'tutor' exists" || echo "WARNING: User 'tutor' does not exist"

# 3. Firewall Status
echo -e "\n--- UFW Status (CRIT-02) ---"
ufw status verbose

# 4. Listening Ports
echo -e "\n--- Open Ports (LISTEN) ---"
ss -tulpn | grep LISTEN | grep -v "127.0.0.1"

# 5. Docker Security
echo -e "\n--- Docker Daemon User ---"
ps aux | grep dockerd | grep -v grep
echo -e "\n--- Running Containers with Privileged Flags ---"
docker ps --format "table {{.Names}}\t{{.Image}}\t{{.Command}}" | grep -i privileged || echo "None"

# 6. Secrets in Config (masked output) - now should show no plaintext secrets
echo -e "\n--- Tutor Config (secrets masked) ---"
grep -E "PASSWORD|SECRET|KEY" /home/tutor/tutor-data/config.yml | sed 's/=.*/=***MASKED***/'

# 7. File Permissions
echo -e "\n--- Critical File Permissions ---"
ls -la /home/tutor/tutor-data/config.yml
ls -la /etc/nginx/sites-available/ 2>/dev/null || echo "Nginx config not found"

# 8. Logs
echo -e "\n--- Recent Syslog Errors ---"
tail -20 /var/log/syslog | grep -i error
echo -e "\n--- Tutor Container Logs (last 5 lines each) ---"
for c in lms cms mfe mysql mongodb redis meilisearch; do
    echo ">>> $c <<<"
    docker logs --tail=5 tutor_local-$c 2>/dev/null || echo "Container not found"
done

# 9. Vulnerability Scan (Trivy installed)
if command -v trivy &>/dev/null; then
    echo -e "\n--- Container Image Vulnerabilities (summary) ---"
    trivy image --severity HIGH,CRITICAL --light overhangio/openedx:21.0.7-main-indigo 2>/dev/null | tail -10
    echo "Trivy scan completed."
else
    echo "WARNING: Trivy not installed (should be resolved)"
fi

# 10. Backup Status
echo -e "\n--- Recent Backup Files (last 7 days) ---"
find /home/tutor/tutor-data/backups -name "*.sql" -o -name "*.tar.gz" -mtime -7 2>/dev/null || echo "No backups found"

# 11. Security Headers Check
echo -e "\n--- Security Headers ---"
curl -sI https://educationvirtual.net | grep -i "x-frame-options\|x-content-type-options\|strict-transport\|x-xss-protection"

# 12. Fail2ban Status
echo -e "\n--- Fail2ban Status ---"
systemctl status fail2ban --no-pager

# 13. Kernel Versions
echo -e "\n--- Installed Kernels ---"
dpkg -l | grep linux-image | awk '{print $2, $3}'

# 14. Memory Usage
echo -e "\n--- Memory Usage (RAM + Swap) ---"
free -h

# 15. Container Health Checks (MED-02)
echo -e "\n--- Container Health Status ---"
docker ps --format "table {{.Names}}\t{{.Status}}"

echo -e "\n=========================================="
echo " Audit complete. All checks passed."
echo "=========================================="
\end{lstlisting}

\subsection{MED-02: Container Health Checks}

Health checks allow Docker to monitor the status of each container and automatically restart unhealthy ones. We will add healthcheck directives to the Tutor Docker Compose override file.

\subsubsection{Step 1: Create docker-compose.override.yml}

Add health checks for each service that supports a status endpoint. Save this as `/home/tutor/tutor-data/env/local/docker-compose.override.yml`.

\begin{lstlisting}[caption={docker-compose.override.yml for health checks}]
services:
  lms:
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8000/health"]
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 60s

  cms:
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8000/health"]
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 60s

  mysql:
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost"]
      interval: 30s
      timeout: 10s
      retries: 3

  mongodb:
    healthcheck:
      test: ["CMD", "mongosh", "--eval", "db.adminCommand('ping')"]
      interval: 30s
      timeout: 10s
      retries: 3

  redis:
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 30s
      timeout: 10s
      retries: 3

  caddy:
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:2019/config/"]
      interval: 30s
      timeout: 10s
      retries: 3

  meilisearch:
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:7700/health"]
      interval: 30s
      timeout: 10s
      retries: 3
\end{lstlisting}

Then restart Tutor:

\begin{lstlisting}[language=bash, caption={Apply health checks}]
cd /home/tutor/tutor-data
tutor local stop
tutor local start
\end{lstlisting}

\subsection{MED-05: Network Segmentation}

Separate Docker networks isolate traffic between frontend (public), backend (application), and database (internal) tiers. This reduces the attack surface.

\subsubsection{Step 1: Create Docker Networks}

\begin{lstlisting}[language=bash]
docker network create frontend
docker network create backend
docker network create database
\end{lstlisting}

\subsubsection{Step 2: Update docker-compose.override.yml}

Assign each service to the appropriate network(s). Only Caddy (reverse proxy) should be on the frontend network. Append the following to your `docker-compose.override.yml`:

\begin{lstlisting}[caption={Network segmentation configuration}]
services:
  caddy:
    networks:
      - frontend
      - backend

  lms:
    networks:
      - backend
      - database

  cms:
    networks:
      - backend
      - database

    networks:
      - backend
      - database

  cms-worker:
    networks:
      - backend
      - database

  mysql:
    networks:
      - database

  mongodb:
    networks:
      - database

  redis:
    networks:
      - database

  meilisearch:
    networks:
      - database

  smtp:
    networks:
      - backend

networks:
  frontend:
    external: true
  backend:
    external: true
  database:
    external: true
\end{lstlisting}

tutor local start

\subsection{MED-06: Security Awareness Program}

A security awareness program educates employees about security risks and their responsibilities. This is a mandatory requirement under CMCSRS 6.13.

\subsubsection{Step 1: Develop a Training Policy}

Create a document that outlines:
- Training frequency (e.g., annually, with quarterly refreshers)
- Topics covered (phishing, password hygiene, data classification, incident reporting)
- Method of delivery (online modules, in‑person sessions, quizzes)

\subsubsection{Step 2: Select Training Materials}

Use free or paid resources:
- \textbf{Open edX itself} can host a course on security awareness.
- External platforms: KnowBe4, SANS Securing the Human, or use INSA's provided materials.
- Create internal slides covering specific risks for the platform (e.g., handling learner PII).

\subsubsection{Step 3: Schedule and Conduct Training}

- Set a quarterly schedule for new hires and annual refreshers for all staff.
- Use a Learning Management System (LMS) like Open edX to deliver and track completion.

\subsection{MED-07: Incident Response Plan}

An Incident Response Plan (IRP) provides a structured approach to detect, contain, and recover from security incidents. This aligns with CMCSRS 6.26.

\subsubsection{Step 1: Create the IRP Document}

Include the following sections:
\begin{enumerate}
    \item \textbf{Preparation}: Roles (CISO, IT, PR, Legal), contact lists, tools.
    \item \textbf{Detection and Analysis}: Monitoring sources (logs, alerts), escalation thresholds.
    \item \textbf{Containment, Eradication, and Recovery}: Steps to isolate affected systems, remove threats, restore services.
    \item \textbf{Post‑Incident Activity}: Lessons learned, evidence preservation, reporting to Ethio‑CERT and INSA (required by CMCSRS 6.26.f).
\end{enumerate}

\subsubsection{Step 2: Define Roles and Responsibilities}

Assign specific personnel:
\begin{itemize}
    \item Incident Commander
    \item Technical Lead (for investigation)
    \item Communications Lead (internal/external)
    \item Legal/Compliance Advisor
\end{itemize}

\subsection{MED-08: Business Continuity Plan}

A Business Continuity Plan (BCP) ensures critical services can continue or be restored quickly after a disruption. This addresses CMCSRS 6.19.

\subsubsection{Step 1: Identify Critical Systems and Dependencies}

List the essential services:
\begin{itemize}
    \item LMS (Learner access)
    \item CMS (Educator authoring)
    \item MySQL (user data, grades)
    \item MongoDB (course structure, discussions)
    \item Media files (uploads, course assets)
\end{itemize}

\subsubsection{Step 2: Define Recovery Objectives}

- \textbf{Recovery Time Objective (RTO)}: Maximum downtime tolerated (e.g., 4 hours for LMS, 24 hours for non‑critical).
- \textbf{Recovery Point Objective (RPO)}: Maximum data loss acceptable (e.g., 1 hour for MySQL).

\subsection{LOW-01: Verbose Error Messages}

Verbose error messages can leak internal information (stack traces, file paths). We must configure the application to show generic error pages to users while logging detailed errors internally.

\subsubsection{Step 1: Disable DEBUG Mode}

Ensure `DEBUG` is set to `False` in the LMS and CMS environment:

\begin{lstlisting}[language=bash]
tutor config save --set DEBUG=False
tutor local restart
\end{lstlisting}

\subsubsection{Step 2: Custom Error Pages}

Create custom error pages (e.g., 404, 500) for Caddy. Add this to your `Caddyfile`:

\begin{lstlisting}[caption={Custom error pages in Caddyfile}]
handle_errors {
    @404 {
        expression {http.error.status_code} == 404
    }
    rewrite @404 /404.html
    file_server {
        root /path/to/error/pages
    }
}
\end{lstlisting}

\subsection{LOW-03: Backup and Recovery}

Regular backups protect against data loss. We will implement automated backups for MySQL, MongoDB, and media files, with off‑site storage.

\subsubsection{Step 1: Create Backup Script}

Create a script `/home/tutor/backup.sh` that dumps databases and archives media.

\begin{lstlisting}[language=bash, caption={backup.sh}]
#!/bin/bash
BACKUP_DIR="/home/tutor/tutor-data/backups"
DATE=$(date +%Y%m%d-%H%M%S)

mkdir -p "$BACKUP_DIR"

# MySQL dump
docker exec tutor_local-mysql-1 mysqldump -uroot -p"$(tutor config printvalue MYSQL_ROOT_PASSWORD)" --all-databases > "$BACKUP_DIR/mysql-$DATE.sql"

# MongoDB dump
docker exec tutor_local-mongodb-1 mongodump --archive="$BACKUP_DIR/mongo-$DATE.archive" --gzip

# Media files (assumes mounted volume)
tar -czf "$BACKUP_DIR/media-$DATE.tar.gz" -C /home/tutor/tutor-data/data/ openedx-media

# Keep only last 7 days
find "$BACKUP_DIR" -type f -mtime +7 -delete
\end{lstlisting}

Make it executable:

\begin{lstlisting}[language=bash]
chmod +x /home/tutor/backup.sh
\end{lstlisting}

\subsubsection{Step 2: Schedule Daily Backup}

Add a cron job to run daily at 2 AM:

\begin{lstlisting}[language=bash]
(crontab -l 2>/dev/null; echo "0 2 * * * /home/tutor/backup.sh") | crontab -
\end{lstlisting}
