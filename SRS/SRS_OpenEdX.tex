\section{Introduction}
\subsection{Purpose}
This document defines the functional and non‑functional requirements for the Moove Education Platform, an Open edX‑based learning management system deployed using Tutor. It serves as the living source of truth for system capabilities, guiding continuous development, internal quality assurance, and security assessment activities. The requirements are aligned with Ethiopian regulatory frameworks, including the Critical Mass Cyber Security Requirement Standard (CMCSRS), the National Cybersecurity Policy, the Computer Crime Proclamation, and the Electronic Signature Proclamation.

\subsection{Scope}
The system provides a comprehensive online learning environment supporting:
\begin{itemize}
    \item Course creation, authoring, and management (Educator features).
    \item Learner enrollment, progression, and engagement (Learner features).
    \item Content delivery (video, text, interactive components).
    \item Assessments (quizzes, assignments, peer reviews, proctored exams).
    \item Collaboration (discussions, teams, wikis).
    \item Analytics and reporting.
    \item Administrative controls.
\end{itemize}

\subsection{System Overview and Actors}
The platform is a client‑server application based on Open edX, deployed in Docker containers orchestrated by Tutor. It uses a microservices architecture with separate containers for LMS, CMS, MFE, databases, and supporting services.

\subsubsection{Actors}
\begin{itemize}
    \item \textbf{Educator (Instructor/Staff)}: Creates and manages courses, creates content, assesses learners, moderates discussions, views analytics.
    \item \textbf{Learner (Student)}: Enrolls in courses, accesses content, completes assessments, participates in discussions, tracks progress.
    \item \textbf{Administrator}: Manages users, courses, site configuration, and system health.
    \item \textbf{System}: Automated processes (notifications, email, background tasks).
\end{itemize}

\subsection{System Constraints}
\begin{itemize}
    \item The system must comply with Ethiopian laws and regulations, including the Computer Crime Proclamation and the Electronic Signature Proclamation.
    \item All user data must be stored and processed within the country’s jurisdiction.
    \item The system must support English and Amharic (planned) interfaces.
    \item The system shall be accessible via modern web browsers and mobile devices.
\end{itemize}

\subsection{Assumptions and Dependencies}
\begin{itemize}
    \item The platform assumes reliable internet connectivity for both learners and educators.
    \item Third‑party services (e.g., video hosting, proctoring) are available and secured.
    \item The underlying Tutor deployment and container infrastructure are maintained and updated regularly.
\end{itemize}

\subsection{Course Creation \& Planning Module}
\paragraph{General Description}
Provides tools for educators to create, plan, and structure courses.

\subsubsection{Requirement UFR-OE-001-01: Create a New Course}
\begin{enumerate}[label=\textbf{\arabic*.}]
\item \textbf{Title:} Create a new course.
\item \textbf{UML Traceability:} Use Case: “Create Course”; Activity: “Course Creation Flow”.
\item \textbf{Actor:} Educator (Instructor/Staff).
\item \textbf{Pre-conditions:} 
    \begin{itemize}
        \item Educator is logged in with course creation permissions.
        \item The organisation code, course number, and run combination is unique.
    \end{itemize}
\item \textbf{Post-conditions:}
    \begin{itemize}
        \item A new course skeleton is created in the CMS.
        \item The course appears in the educator’s course list.
        \item An audit log entry is recorded.
    \end{itemize}
\item \textbf{Normal Flow:}
    \begin{enumerate}
        \item Educator navigates to Studio (CMS).
        \item Clicks “New Course”.
        \item Enters course title, organisation code, course number, and course run.
        \item Sets start date, enrollment start/end dates, and course visibility.
        \item Clicks “Create”.
        \item System validates uniqueness and creates the course ID.
    \end{enumerate}
\item \textbf{Alternative Flows:}
    \begin{itemize}
        \item Alt 1: Duplicate course ID → validation error.
    \end{itemize}
\item \textbf{Business Rules:} Course ID format: \texttt{org+course+run}; must be unique.
\item \textbf{Input/Output:} Input: title, org, number, run, start date, enrollment dates. Output: Course object with ID.
\item \textbf{Acceptance Criteria:}
    \begin{verbatim}
Given I am an educator
When I create a course with title "Introduction to Physics"
Then I receive a 201 Created
And the course appears in my course list
    \end{verbatim}
\end{enumerate}

\section{Security and Compliance Requirements (Non‑Functional)}
This section defines mandatory security requirements derived from INSA’s CMCSRS, the Computer Crime Proclamation, and the Electronic Signature Proclamation. All requirements are traceable to the \textit{Security Architecture \& Threat Model} document.

\subsection{Access Control (CMCSRS 6.17)}
\begin{enumerate}[label=\textbf{SEC-NFR-001-\arabic*.}]
    \item The system must enforce role‑based access control (RBAC) for all user actions.
    \item All access to administrative functions must be restricted to users with appropriate privileges.
    \item User accounts must be subject to a formal provisioning and de‑provisioning process.
    \item Default passwords for any system component must be changed upon first use.
    \item The system must implement multi‑factor authentication (MFA) for administrative accounts.
\end{enumerate}

\subsection{Cryptography (CMCSRS 6.18)}
\begin{enumerate}[label=\textbf{SEC-NFR-002-\arabic*.}]
    \item All data in transit must be encrypted using TLS 1.2 or higher.
    \item All sensitive data at rest must be encrypted using strong, INSA‑approved algorithms.
    \item Private keys and secrets must never be stored in plaintext.
    \item Digital signatures must be used for certificate verification as per the Electronic Signature Proclamation.
\end{enumerate}

\subsection{Network Security (CMCSRS 5.7.c)}
\begin{enumerate}[label=\textbf{SEC-NFR-003-\arabic*.}]
    \item A host‑based firewall must be active and configured to allow only necessary ports.
    \item The internal network must be segmented into separate Docker networks.
    \item All unnecessary services and ports must be disabled.
    \item Intrusion detection/prevention systems must be deployed.
\end{enumerate}

\subsection{Logging and Monitoring (CMCSRS 6.25)}
\begin{enumerate}[label=\textbf{SEC-NFR-004-\arabic*.}]
    \item All logs must be collected centrally and retained for at least one month.
    \item Security‑relevant events must be logged with timestamps and user identifiers.
    \item Regular vulnerability scanning must be performed weekly.
    \item Anomaly detection and alerting must be configured.
\end{enumerate}

\subsection{Incident Response and Business Continuity (CMCSRS 6.26, 6.19)}
\begin{enumerate}[label=\textbf{SEC-NFR-005-\arabic*.}]
    \item An incident response plan must be documented and tested annually.
    \item A business continuity plan with defined RTO and RPO must be maintained.
    \item Regular backups must be performed and stored off‑site.
    \item All security incidents must be reported to Ethio‑CERT and INSA.
\end{enumerate}

\subsection{Personnel Security (CMCSRS 5.6, 6.37)}
\begin{enumerate}[label=\textbf{SEC-NFR-006-\arabic*.}]
    \item All personnel with access to sensitive systems must undergo security clearance.
    \item Mandatory annual security awareness training must be provided.
    \item Job descriptions must include security responsibilities.
\end{enumerate}

\subsection{Compliance and Audit (CMCSRS 6.21, 6.22, 6.23)}
\begin{enumerate}[label=\textbf{SEC-NFR-007-\arabic*.}]
    \item The system must undergo an annual security audit by an INSA‑certified auditor.
    \item All information systems must be accredited before deployment.
    \item A compliance report must be submitted to INSA annually.
\end{enumerate}

\section{Non‑Functional Requirements}
\subsection{Performance}
\begin{itemize}
    \item Support at least 10,000 concurrent learners and 500 concurrent educators.
    \item Page load times below 2 seconds for 95\% of requests.
    \item API response times below 500ms for 95\% of requests.
    \item Video streaming supports at least 720p with adaptive bitrate.
\end{itemize}

\subsection{Security}
\begin{itemize}
    \item All network communication encrypted with TLS 1.2+.
    \item Passwords hashed using PBKDF2/BCrypt.
    \item API authentication using JWT with short expiry.
    \item RBAC enforced.
    \item Firewall and intrusion detection in place.
\end{itemize}

\subsection{Availability}
\begin{itemize}
    \item 99.9\% uptime.
    \item Automatic container restarts.
    \item Daily off‑site backups.
\end{itemize}

\subsection{Maintainability}
\begin{itemize}
    \item Containerised microservices architecture.
    \item Quarterly upstream merges.
    \item Externalised configuration.
\end{itemize}

\subsection{Scalability}
\begin{itemize}
    \item Horizontal scaling with container replicas.
    \item Database read replicas supported.
\end{itemize}

\subsection{Usability}
\begin{itemize}
