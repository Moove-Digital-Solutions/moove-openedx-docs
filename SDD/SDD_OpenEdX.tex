\section{System Overview}
Moove Education Platform is an Open edX instance deployed using Tutor (v21.0.8) on Ubuntu 22.04. The architecture is container-based (Docker) and microservices-oriented. All components are orchestrated by Tutor and run inside Docker containers, with Caddy acting as the reverse proxy and TLS terminator.

\section{Physical Architecture}
The deployment consists of the following containers:
\begin{itemize}
    \item \textbf{LMS (Learning Management System)}: Learner-facing operations (courses, enrollments, assessments). Runs uWSGI.
    \item \textbf{CMS (Course Management System)}: Educator authoring interface (Studio).
    \item \textbf{LMS Worker / CMS Worker}: Celery workers for background tasks.
    \item \textbf{MFE (Micro-Frontends)}: Serves modern frontend applications via Caddy.
    \item \textbf{Caddy}: Reverse proxy and automatic TLS (ports 80/443).
    \item \textbf{MySQL 8.4}: Primary relational database.
    \item \textbf{MongoDB 7.0}: Course structure and discussion data.
    \item \textbf{Redis 7.4}: Caching and Celery broker.
    \item \textbf{Meilisearch 1.8}: Search engine.
    \item \textbf{SMTP (Exim)}: Email relay.
\end{itemize}

\section{Logical Architecture}
\subsection{Presentation Layer}
- MFE apps (Account, Authn, Learner Dashboard) via Caddy.
- Django templates for legacy parts.

\subsection{Business Logic Layer}
- Django/EdX-platform (Python) with plugins (Indigo theme, MFE).
- Celery for asynchronous tasks.

\subsection{Data Layer}
- MySQL: Users, courses, grades, enrollments.
- MongoDB: Course structures, discussions.
- Redis: Session, cache, Celery broker.
- Meilisearch: Search index.

\section{System Architecture and Data Flow}

\subsection{Key Components}
The Moove Education Platform consists of the following main components:
\begin{itemize}
    \item \textbf{Reverse Proxy / TLS Termination:} Caddy handles all external HTTPS traffic, terminates TLS, and routes requests to the appropriate internal services.
    \item \textbf{Learning Management System (LMS):} Django application that serves learner‑facing pages, handles enrollments, assessments, and grading.
    \item \textbf{Course Management System (CMS):} Django application (Studio) used by educators to author and manage courses.
    \item \textbf{Micro‑Frontends (MFE):} React‑based frontend applications (Account, Authn, Learner Dashboard) served via Caddy.
    \item \textbf{Background Workers:} Celery workers for asynchronous tasks (email, grading, analytics).
    \item \textbf{Primary Databases:} MySQL for user, course, and grade data; MongoDB for course structure and discussion data.
    \item \textbf{Caching and Messaging:} Redis for session storage, caching, and Celery broker.
    \item \textbf{Search Engine:} Meilisearch for full‑text search across courses and content.
    \item \textbf{Email Relay:} SMTP (Exim) for sending system emails.
\end{itemize}

\subsection{System Architecture Diagram}
The following diagram illustrates the high‑level system architecture, showing how components interact and the network segmentation used to isolate services.

\begin{figure}[H]
\centering
\includegraphics[width=\textwidth,height=0.7\textheight,keepaspectratio]{diagrams/system_architecture.png}
\caption{System Architecture Diagram showing Caddy, LMS, CMS, MFE, databases, and supporting services.}
\label{fig:system_arch}
\end{figure}

\subsubsection*{Explanation of the System Architecture Diagram}
This diagram depicts the entire Moove Education Platform as a set of networked components grouped into three logical networks: \textbf{Frontend}, \textbf{Backend}, and \textbf{Database}.

- \textbf{External Users} (Learners, Educators, Administrators) connect to the system over the internet via HTTPS.
- \textbf{Caddy} acts as the single entry point (reverse proxy). It terminates TLS, routes requests to the appropriate service, and serves static assets. It also provides load balancing and automatic certificate renewal via Let's Encrypt.
- The \textbf{Frontend Network} contains only Caddy, which is exposed to the internet on ports 80 and 443.
- The \textbf{Backend Network} hosts the core application services:
  \begin{itemize}
    \item \textbf{LMS (Django)}: handles all learner operations, including enrollment, content delivery, assessments, and grading.
    \item \textbf{CMS (Django)}: the Studio interface for educators to create and manage courses.
    \item \textbf{MFE (React)}: micro‑frontend applications that provide modern user interfaces for authentication, account management, and learner dashboard.
    \item \textbf{Celery Workers}: process asynchronous tasks such as sending emails, grading background jobs, and updating analytics.
    \item \textbf{SMTP Relay (Exim)}: sends system emails (notifications, confirmations) to users.
  \end{itemize}
- The \textbf{Database Network} is isolated from the backend and contains all persistent data stores:
  \begin{itemize}
    \item \textbf{MySQL 8.4}: stores relational data (users, courses, enrollments, grades, etc.).
    \item \textbf{MongoDB 7.0}: stores course structure (XBlock content) and discussion forum data.
    \item \textbf{Redis 7.4}: used for caching, session storage, and as a message broker for Celery.
    \item \textbf{Meilisearch 1.8}: provides fast full‑text search over course content and discussions.
  \end{itemize}

Connections between components are shown with arrows:
- Caddy proxies requests to LMS, CMS, MFE, and Meilisearch.
- LMS and CMS communicate with MySQL, MongoDB, and Redis.
- LMS interacts with Celery (via Redis) and SMTP.
- MFE communicates with LMS and CMS via REST APIs.
- Workers access MySQL, MongoDB, and SMTP for background tasks.

This separation into networks enforces security boundaries: only Caddy is exposed externally; all other services are internal and accessible only within the Docker environment.

\subsubsection{Level 1 DFD}
The Level 1 DFD shows the main processes within the system and how they interact with data stores and external entities.

\begin{figure}[H]
\centering
\includegraphics[width=\textwidth,height=0.7\textheight,keepaspectratio]{diagrams/dfd_level1.png}
\caption{Level 1 DFD showing main processes: Authentication, Course Management, Enrollment, Content Delivery, Assessment, and Reporting.}
\label{fig:dfd_level1}
\end{figure}

\subsubsection*{Explanation of the Level 1 DFD}
This diagram decomposes the system into six core processes and three data stores:

\textbf{Processes:}
\begin{enumerate}
    \item \textbf{Authenticate} – validates user credentials (learner, educator, admin). Interacts with MySQL (user table) and Redis (session storage).
    \item \textbf{Manage Courses} – handles course creation, updates, and publishing. Writes course metadata to MySQL and course structure (outline) to MongoDB.
    \item \textbf{Enroll} – manages learner enrollment. Writes enrollment records to MySQL and triggers a Celery task (via Redis) to send a confirmation email.
    \item \textbf{Deliver Content} – retrieves course content based on learner requests. Reads course metadata from MySQL and course structure from MongoDB; uses Redis for caching.
    \item \textbf{Assess} – processes learner answers, stores grades in MySQL, and queues grading tasks via Redis.
    \item \textbf{Report} – generates analytics and search results. Queries MySQL for aggregate data and uses Meilisearch for full‑text search.
\end{enumerate}

\textbf{Data Stores:}
\begin{itemize}
    \item \textbf{MySQL}: persistent storage for users, courses, grades, enrollments, and other relational data.
    \item \textbf{MongoDB}: stores course structure (hierarchical content) and discussion data.
    \item \textbf{Redis}: serves as a cache, session store, and Celery broker for asynchronous tasks.
\end{itemize}

Data flows between processes and stores are labelled with the type of operation (read/write). The diagram also shows that the Enroll process communicates with Deliver (enrollment status affects content visibility) and Manage Courses feeds published courses to Deliver.

\subsection{Data Flow Explanation}
The system processes data as follows:

\begin{itemize}
    \item \textbf{Authentication:} User credentials are submitted via the MFE or LMS. Caddy passes the request to the LMS, which validates against MySQL and returns a session token (JWT).
    \item \textbf{Course Management:} Educators create course structures in the CMS. Data is stored in MySQL (course metadata) and MongoDB (course outline, XBlock content). When published, the LMS reads this data to render course content.
    \item \textbf{Enrollment:} When a learner enrolls, the LMS writes the enrollment record to MySQL and triggers a Celery task to send a confirmation email.
    \item \textbf{Content Delivery:} Learners request course pages; the LMS fetches the course structure from MongoDB, renders the content (using Django templates or MFE), and serves it via Caddy.
    \item \textbf{Assessments:} Learner answers are sent to the LMS, validated, and stored in MySQL. Grade calculations are performed asynchronously by Celery workers.
    \item \textbf{Search:} Meilisearch indexes course content and discussions. Search queries are routed through Caddy to the Meilisearch API.
    \item \textbf{Notifications:} The system generates notification events (e.g., discussion replies, assignment due dates) via Redis and Celery, sending emails through the SMTP relay.
\end{itemize}

\section{Security Architecture (INSA Compliance)}
This section describes the security controls implemented to meet INSA requirements. Detailed risk assessment and threat modelling are provided in the \textit{Security Architecture \& Threat Model} document.

\subsection{Network Security}
\begin{itemize}
    \item Host firewall (UFW) is enabled and configured to allow only SSH (22), HTTP (80), and HTTPS (443) from external networks.
    \item Internal container networking is segmented into three Docker networks: \texttt{frontend}, \texttt{backend}, and \texttt{database}. The database network is internal and not exposed to the host.
    \item All unnecessary ports and services are disabled.
    \item Rate limiting and brute‑force protection are provided by fail2ban.
\end{itemize}

\subsection{Container Isolation}
\begin{itemize}
    \item Each service runs in its own container with minimal privileges.
    \item Tutor runs under a dedicated non‑root user (\texttt{tutor}) with membership in the \texttt{docker} group.
    \item Resource limits (CPU, memory) are applied to containers to prevent resource exhaustion.
\end{itemize}

\subsection{Secrets Management}
\begin{itemize}
    \item All sensitive configuration values (passwords, API keys, private keys) are stored encrypted and rotated regularly.
    \item Secrets are managed via Tutor's configuration system and not hard‑coded in source code.
    \item JWT RSA private key is stored securely and rotated periodically.
\end{itemize}

\subsection{Monitoring and Logging}
\begin{itemize}
    \item Centralised logging is implemented using Tutor log analysis.
    \item Security events (login failures, privilege changes) are logged and monitored.
    \item Weekly vulnerability scanning of container images is performed using Trivy.
\end{itemize}

\subsection{Compliance}
\begin{itemize}
    \item The architecture is designed to meet CMCSRS requirements for access control, cryptography, and incident response.
    \item Annual security audits and accreditation are planned.
    \item All security controls are documented and tested.
\end{itemize}

For a complete threat model and risk assessment, refer to the \textit{Security Architecture \& Threat Model} (Security\_OpenEdX.tex).

\subsection{Class Diagram}
The Class Diagram shows the core entities and their relationships.

\begin{figure}[H]
\centering
\includegraphics[width=\textwidth,height=0.7\textheight,keepaspectratio]{diagrams/class.png}
\caption{Core entities: User, Course, Enrollment, Assessment, Grade, Discussion.}
\label{fig:class}
\end{figure}

\subsubsection*{Explanation of the Class Diagram}
This diagram defines the main domain classes and their associations, which map to the database tables.

- \textbf{User}: represents a platform user (learner, instructor, admin). Attributes include \texttt{id}, \texttt{username}, \texttt{email}, \texttt{password\_hash}, \texttt{is\_staff}, \texttt{is\_superuser}, \texttt{last\_login}.

- \textbf{Course}: a course offering. Attributes: \texttt{id} (course key), \texttt{display\_name}, \texttt{start}, \texttt{end}, \texttt{enrollment\_track}, \texttt{is\_published}.

- \textbf{Enrollment}: links a User to a Course. Attributes: \texttt{created}, \texttt{is\_active}, \texttt{mode} (audit/verified). Multiplicity: a User can have many Enrollments; a Course can have many Enrollments.

- \textbf{Assessment}: a learning activity (quiz, assignment, peer review). Attributes: \texttt{section}, \texttt{type}, \texttt{max\_score}. Each Course has multiple Assessments.

- \textbf{Grade}: a score for a User on a specific Assessment in a Course. Attributes: \texttt{score}, \texttt{percent}, \texttt{passed}. Links User, Course, and Assessment.

- \textbf{DiscussionThread}: a forum topic within a Course. Attributes: \texttt{title}, \texttt{created}. Each Course has many Threads; a User can author many Threads.

- \textbf{DiscussionPost}: a reply within a Thread. Attributes: \texttt{body}, \texttt{created}. Each Thread has many Posts; a User can author many Posts.

The relationships are shown with multiplicities (e.g., 1–*, 0–*). This class model underpins the relational database schema and the object‑relational mapping (Django ORM).

\subsection{Sequence Diagram: Course Enrollment}
The Sequence Diagram shows the flow of a learner enrollment process.

\begin{figure}[H]
\centering
\includegraphics[width=\textwidth,height=0.7\textheight,keepaspectratio]{diagrams/sequence_enrollment.png}
\caption{Learner enrollment flow.}
\label{fig:enrollment}
\end{figure}

\subsubsection*{Explanation of the Enrollment Sequence Diagram}
This diagram illustrates the step‑by‑step interaction for a learner enrolling in a course.

\begin{enumerate}
    \item The \textbf{Learner} sends a \texttt{POST /api/enrollment/v1/} request to the \textbf{LMS}.
    \item The LMS inserts a new record into the \textbf{MySQL} database (\texttt{course\_enrollment} table). MySQL confirms success.
    \item The LMS then initialises discussion data for the learner in \textbf{MongoDB} (e.g., creating a discussion topic if needed). MongoDB confirms.
    \item The LMS queues an asynchronous task to send a confirmation email by pushing a message to \textbf{Celery} (via Redis).
    \item The Celery worker processes the task and sends an email to the Learner.
    \item Finally, the LMS returns a \texttt{201 Created} response to the Learner.
\end{enumerate}

This sequence shows synchronous operations (database writes) and asynchronous tasks (email) to maintain responsiveness.

\subsection{Sequence Diagram: Course Creation (Educator)}
The Sequence Diagram shows the flow of an educator creating a course.

\begin{figure}[H]
\centering
\includegraphics[width=\textwidth,height=0.7\textheight,keepaspectratio]{diagrams/sequence_course_creation.png}
\caption{Educator course creation flow.}
\label{fig:course_creation}
\end{figure}

\subsubsection*{Explanation of the Course Creation Sequence Diagram}
This diagram details the process of creating a new course from the CMS.

\begin{enumerate}
    \item The \textbf{Educator} clicks “New Course” in the Studio UI.
    \item The \textbf{CMS} validates the proposed course ID (ensuring uniqueness).
    \item The CMS inserts a new row into the \textbf{MySQL} \texttt{course\_overview} table with course metadata. MySQL returns success.
    \item The CMS initialises the course structure in \textbf{MongoDB} (e.g., creates the root node for the course). MongoDB confirms.
    \item The CMS returns a confirmation to the Educator that the course skeleton has been created.
\end{enumerate}

This sequence is synchronous; the course is immediately ready for further content editing.
